# PCB, credits, security, and hosting launch plan

> The audit and dedicated-engine costs below are historical. The current user-approved approach runs the original engine in a paired local runtime. See [LOCAL_RUNTIME.md](LOCAL_RUNTIME.md) for the active architecture, pricing, limits and deployment settings. `render.yaml` provisions only the free Node API.

Status: implementation in progress, 4 October 2026. The historical findings and cost examples below remain the original planning baseline. See [the launch runbook](LAUNCH_RUNBOOK.md) for the current release gates. Billing is disabled in `render.yaml` until the external checks are complete.

**Implemented in this workspace:** INR credit packs and Stripe Checkout/webhook ledger, trial grant and five free hosted design chats with an included pipeline and PCB run, fixed server-side quotes and transactional reservations, refund/dispute reversal, settings/landing pricing, a Redis-backed AI worker with persistent job records, project/job/artifact authorization, server-side design persistence, input caps, and an isolated board evaluation path. Groq token usage is now captured from Python LangChain calls and designer calls and stored on charges for calibration. The current debit is the published fixed quote; the illustrative variable-cost formula below is not yet active.

**Still required before paid production:** Stripe India account and tax/invoice configuration; test-mode checkout and signed webhook against the real account; Render/Vercel/Atlas provisioning; Linux bubblewrap smoke test in the actual private engine; independent Gerber/drill/ERC fixtures and human fabrication approval; 100+ real usage samples and tariff/margin review; private object storage and migration of any old public Cloudinary assets. Gerber downloads remain blocked by the backend until fabrication checks exist. No account or infrastructure has been deployed from this repository.

## 1. What the project does today

The Next.js frontend calls an Express/MongoDB backend. The backend calls only the Python Supervisor. The Supervisor runs the Groq-based requirements, architecture, component, PCB handoff, validation, and documentation pipeline. A separate `dunkai-designer` Node process turns `pcb_ir` into a tscircuit board, SVG/GLB previews, BOM, placement CSV, and Gerbers. The backend relays Supervisor SSE events to Socket.io rooms. It stores the final board record; most other pipeline artifacts are saved later by the browser.

The original audit found monthly `Usage` counters and manual plan links. The new implementation uses wallet balances, a credit ledger, and Stripe Checkout when `BILLING_ENABLED=true`. The current Render blueprint leaves billing off while deployment and payment verification are pending.

## 3. Credit offer and economics (India, proposed)

**Offer (updated 8 October 2026):** freemium with prepaid top-ups. Every verified account gets **5 design chats per calendar month (UTC)**, each including its requirements interview, one completed design pipeline and one PCB generation at **0 credits**. Failed operations can retry their included run; a failed first request returns the monthly slot. Extra completed pipeline or PCB generations cost the published quotes. Existing accounts receive the allowance independently of leftover trial credits. A new verified account retains the **150 one-time trial-credit bonus** for additional work. Unused monthly slots do not accumulate; an already-started chat can finish its included design after the month changes. Paying users receive the same five free design chats. Stripe checkout is configured in test mode until live credentials and a matching live webhook are supplied. The cost illustration below describes additional paid work, not charges for these included designs.

**Unit:** 1 paid credit = ₹1 of prepaid value. Start with simple, undiscounted packs: **200 credits/₹200, 500/₹500, and 1,500/₹1,500**. Credits are an internal consumption unit, not transferable cash. Paid credits do not expire. Trial credits are consumed before paid credits; both follow the same quoted operation prices. Tax handling and invoice wording must be reviewed for the merchant's Indian entity before launch. Stripe India currently says standard domestic cards are 2% and international cards 3%, with more cases for cross-border/currency conversion; its India page says to request an invite. Confirm account activation, permitted products, payout currency, and actual negotiated fees before taking payments.

Use **Groq `openai/gpt-oss-120b`** as the only operator-paid launch model, with other provider choices BYOK until their costs have their own meter. Its published price is $0.15 per million input tokens and $0.60 per million output tokens; cached input has a different rate. Record the actual model and cached/uncached token counts for *every* Groq call, including safety checks, retries that were billed, pipeline agents, and the designer. Python agents currently do not send that ledger to the backend; the designer only logs some total token counts. Until end-to-end metering exists, these are planning estimates rather than a billable tariff.

Planning exchange rate: **₹100 per USD**, deliberately rounded and reviewed monthly. Suggested initial charge per operation:

`credits = ceil(max(operation_floor, 5 × actual_provider_cost_INR + operation_compute_reserve))`

| Operation | Floor | Compute reserve | Example tokens, input/output | Groq cost at ₹100/$ | Estimated debit |
| --- | ---: | ---: | ---: | ---: | ---: |
| AI chat turn | 2 | 1 | 6k / 1.5k | ₹0.18 | 2 |
| Full design pipeline | 25 | 10 | 120k / 35k | ₹3.90 | 30 |
| Groq PCB generation | 80 | 20 | 600k / 120k | ₹16.20 | 101 |
| Example project: pipeline + one board + five chats | — | — | 750k / 162.5k combined | ₹21.00 | **about 141 credits before free turns; 131 wallet credits when all five chats are free** |

The token counts are **illustrative assumptions**, not measured distributions. A smaller project may use fewer than 100 credits; a large project with repairs and repeated boards may use 200–400+. Collect at least 100 real, anonymized jobs by operation and component count, then publish median, p90, and worst-case credit examples. Show the cost estimate and a hard maximum before starting each job. Reserve that maximum atomically; stop or request a new quote before exceeding it; settle against actual metered usage and release the rest. For BYOK, charge no AI-token markup, but charge 10 credits for pipeline compute and 20 for board compute/export; update the current “unlimited BYOK” copy before this policy goes live. Track free turns and trial credits separately from paid credits so a grant cannot be confused with cash received through Stripe.

At 141 paid credits, domestic Stripe's cited 2% is about ₹2.82 per project equivalent, and the example Groq spend is ₹21. This leaves roughly ₹117 **before** Render, Vercel, Atlas, storage/egress, taxes, support, retries, refunds, and failed jobs. At 131 credits after five free turns, paid contribution is roughly ₹107 before fixed costs. A trial project brings in **₹0** and spends roughly ₹21 in Groq usage, so free grants are a controlled acquisition budget, not profit. Initial 24/7 compute example: Render backend `0.5c-512mb` $7/month + engine `1c-2g` $25/month + Vercel Pro $20/month ≈ $52 or ₹5,200/month at the planning FX, excluding Atlas, storage, bandwidth, and taxes. If these additional costs are ₹2,000/month, fixed hosting is ~₹7,200/month: at 100 paid example projects/month that is ₹72/project, leaving roughly ₹35–45/project before support, tax, and trial acquisition cost. At 50 paid projects/month this offer would likely lose money. Track realized gross margin and revisit floors, pack prices, and engine size monthly. Render's 2 GB engine size is a starting point, not a measured memory guarantee.

## 4. Stripe and ledger implementation contract

1. Create `Wallet` (`user`, integer `available`, integer `reserved`) and append-only `CreditEntry` (`user`, `jobId`, `kind`, signed credits, cost metadata, unique idempotency key). Add `Payment`/`StripeEvent` with unique session/event IDs. Use MongoDB transactions (Atlas replica set) or a carefully designed atomic state machine; never derive balance from client data. A repeated webhook, retry, or completion event must be harmless.
2. `POST /billing/checkout`: authenticated, accepts only a server-defined pack ID. Server creates a Stripe Checkout Session in INR paise with fixed amount and internal user/pack reference. Browser receives only the Checkout URL. Success redirect does not grant credits.
3. Mount the webhook route **before** `express.json()` so Stripe sees its exact raw body. Verify `Stripe-Signature`, then check session `payment_status`, currency, total, environment mode, pack, and user against the server-created order. Grant once on `checkout.session.completed` with paid status (and handle delayed success events if enabled). Record refunds/disputes as compensating entries and freeze or recover spent negative balances by policy.
4. On AI start, validate access and input, create `Job` with immutable owner/project/chat/action/model/version, reserve quoted maximum, enqueue once, then return job ID. On completion, collect all provider usage events, compute the debit from the versioned tariff, settle the reserve, store final artifacts and cost, then notify sockets. On pre-start failure, release all. On mid-run failure/cancel, settle only documented incurred usage plus the disclosed compute amount. Reconcile stuck reservations with a timed worker.
5. Expose `GET /billing/wallet`, `GET /billing/entries`, `GET /billing/quote`, and checkout creation. Update settings/pricing UI and replace conflicting monthly plan claims only once the ledger and Stripe test-mode webhook are passing. Keep an explicit no-charge BYOK rule for Groq token cost, with the separately disclosed board compute fee.
6. Test webhook signature rejection, duplicate and reordered events, unpaid/amount mismatch, cross-user job access, concurrent last-credit reservations, refund/cancel, provider retries, process restart, and reconciliation. Do not enable `BILLING_ENABLED` on production until these pass in Stripe test mode.

Sources: [Groq model prices](https://console.groq.com/docs/model/openai/gpt-oss-120b), [Stripe India pricing and invite status](https://stripe.com/in/pricing), [Stripe Checkout fulfillment](https://docs.stripe.com/checkout/fulfillment.md?payment-ui=stripe-hosted), [Stripe raw-body signature rules](https://docs.stripe.com/webhooks/signature).

## 5. Render + Vercel deployment

```text
Browser -> Vercel Next.js (/api rewrite) -> Render public Express/Socket.io
                                        -> MongoDB Atlas (private credentials)
                                        -> Render private Supervisor/board worker
                                        -> Groq + component catalog
Board/user artifacts -> private object storage -> short-lived authorized URLs
Stripe -> Render Express raw-body webhook -> MongoDB wallet ledger
```

1. **First release:** Vercel project root `frontend/`; Render public backend Docker service from `backend/Dockerfile`; Render **private** AI engine from `ai_engine/Dockerfile` with repository-root Docker context; Atlas MongoDB. Keep one backend instance while job state and Socket.io rooms live in memory. Set `BACKEND_URL` in the Vercel **build** environment for rewrites, `NEXT_PUBLIC_BACKEND_URL` to the public Render backend for sockets, and `FRONTEND_URL`/CORS to the exact Vercel production origin. Use the same strong `SUPERVISOR_AGENT_TOKEN` on backend and engine. Put Groq and Hugging Face keys only on the engine; Stripe secret and webhook key only on backend.
2. **Jobs:** Move board generation to a durable queue and worker before paid launch. A long-running HTTP/SSE connection and in-memory job map (`supervisor.service.js`) are vulnerable to deploys and restarts. Use Render Key Value/Redis or another durable queue and persistent job records. Add Socket.io Redis adapter before scaling backend above one instance. Worker should be separated from the web-facing Supervisor where possible, especially because it executes generated code.
3. **Artifacts:** Prefer S3-compatible private object storage over Render disks for user/board outputs. Render disks preserve only their mount path, attach to one instance, prevent horizontal scaling, and stop zero-downtime deploys. If a disk is used for the initial engine cache, mount `/data` as documented and define backup, retention, and cleanup. Atlas needs backups and connection allowlisting. Do not put MongoDB itself on an app disk.
4. **Release checks:** health endpoints, CORS/socket handshake, Google callback, payment webhook signature, 2 MB API limit versus board URLs, private artifact authorization, board completion after browser disconnect, and real board runs with known-good and deliberately bad IR. Monitor per-job token use, model, DRC, runtime, storage, credit debit, refund, and margin. Alert on negative balances, unmatched Stripe events, stuck jobs, and rapid Groq spend.

Sources: [Render compute plans](https://render.com/docs/compute-plans), [Render pricing](https://render.com/pricing), [Render private services](https://render.com/docs/private-services), [Render disk limitations](https://render.com/docs/disks), [Render workers](https://render.com/docs/background-workers), [Vercel pricing](https://vercel.com/pricing), [Vercel function limits](https://vercel.com/docs/functions/limitations).

## 6. Order of work

### LLM call reduction completed first

The requirements agent no longer forces four questions. It can finish a sufficiently specified PCB brief on its first model response; a detailed brief targets at most two follow-up questions, while a sparse one targets four. If the model still finds a critical gap at the target, it may ask again up to the configured absolute cap instead of failing the run. The synchronous Supervisor now uses the same single-stage revision routing as the streaming endpoint. Inferred revisions run the safety classifier before the selected stage.

For planning, a brief that completes immediately uses about **three pre-board Groq calls**: safety, requirements, and architecture. Two follow-up answers make that about seven calls; four make it about eleven. Options backfill, model retries, and board synthesis can add calls. These are control-flow counts, **not measured token usage or provider charges**; keep the credit prices provisional until per-call telemetry exists.

1. Close P0 access and generated-code isolation issues; fix net collision and fabrication-export gating; add PCB fixture runs with independent Gerber/drill validation.
2. Persist IR/jobs/artifacts server-side; add queue, timeouts, per-user concurrency, and usage telemetry across all Groq calls.
3. Measure 100+ jobs; calibrate quote caps, credit floors, free trial, and INR prices to real costs and target margin.
4. Implement wallet/Stripe test mode, reconciliation, UI, and abuse controls. Verify India Stripe activation and tax/invoice setup.
5. Deploy private engine + public backend on Render, frontend on Vercel, Atlas and private object storage; run end-to-end payment and PCB smoke tests; only then turn on paid billing.
